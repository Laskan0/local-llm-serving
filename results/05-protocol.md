# Протокол нагрузочного эксперимента

Протокол зафиксирован до основной серии. Пробные запросы находятся в `05-benchmark/pilot` и не входят в итоговые сравнения.

## Среда

MacBook Air M4, 16 ГБ общей RAM; Linux ARM64 в Docker Desktop с 10 ГиБ, Minikube 8 vCPU / 9000 МиБ. Один серверный Pod: CPU request 5 / limit 6, RAM request 6 ГиБ / limit 7680 МиБ. Пять OpenMP-потоков закреплены за CPU 0–4 виртуальной машины. vLLM 0.27.1+cpu, Qwen2.5-1.5B-Instruct, BF16 без квантизации, ревизия из `config/model.json`. Это тест всей локальной цепочки через kubectl port-forward, а не отдельного ядра модели.

## Нагрузка и порядок

1. Пробный прогон: 4 коротких запроса при C=1, для проверки SSE/usage. Затем пересоздание Pod, очищающее KV-кэш.
2. **A-before**, пакет 1024: вход 128 и 2048 токенов, по 12 запросов при C=1, 2, 4; всего 72 измеряемых запроса.
3. **B**, пакет 512: те же входы C=4, по 12 запросов; всего 24.
4. **A-after**, возврат пакета 1024: повтор двух точек C=4; ещё 24. Проверка влияния порядка тестов, без заявления о полном контроле температуры.

Во всех сериях: `max_tokens=64`, `ignore_eos=true`, `temperature=0`, `seed=42`, streaming с `include_usage=true`. Успех требует HTTP 200, первого содержательного фрагмента, `[DONE]`, usage с точными длинами и finish_reason=length. Отдельный таймаут ожидания сетевых операций — 240 секунд; автоматических повторов нет. Ошибочные попытки сохраняются.

Таймаут сетевого ожидания не является общим дедлайном ответа: поток может длиться больше 240 секунд, если данные продолжают поступать без такого длительного перерыва. Например, максимальная Latency в длинной точке B составила 256,02 с при успешном завершении.

Перед каждой точкой выполняются C параллельных прогревочных запросов полной длины, их метрики исключаются из производительности. Входы для прогрева отделены от измеряемых. Каждая точка имеет собственные входы; для одного C входы совпадают между A/B/A. После смены настройки создаётся новый Pod; веса остаются на PVC. Между измерениями не выполняются сборки и другие тяжёлые операции проекта. Прочая активность macOS не контролируется.

Синтетические входы состоят из случайной метки и нейтральных английских слов, обрамлённых Qwen chat-токенами. Они подготовлены токенизатором именно закреплённой модели; API получает готовые token IDs через `/v1/completions`. Вход ровно 128 или 2048 токенов, включая обрамление. Проверяется уникальность первых 16 токенов; полный общий префикс искусственно не прогревается. Качество и смысл ответа не оцениваются. Ответы не сохраняются.

Нагрузка закрытая: C работников отправляют следующий запрос после завершения своего предыдущего, без think time. Не измеряются Poisson/open-loop поток, смешанные короткие/длинные запросы, очередь при C>4, длительный soak и производственный SLO.

## Определения метрик

- **TTFT**: perf_counter от начала HTTP-вызова до первого непустого текстового SSE-фрагмента. Пустые и служебные события не считаются токеном. Включает клиентскую сеть, port-forward и очередь сервера; один фрагмент может содержать несколько токенов.
- **Latency**: от того же начала до EOF всего HTTP-потока, после `[DONE]` и usage.
- **Requests/s**: число успешных запросов / общее время точки от одновременного выпуска работников до завершения последнего ответа. Время ошибочных попыток остаётся в знаменателе.
- **Output tokens/s**: сумма фактических выходных токенов успешных запросов из usage / то же общее время. Входные токены сюда не входят; это пропускная способность всей группы, а не скорость одного пользователя.
- **Median**: медиана успешных запросов. **p95**: nearest rank `ceil(0.95*N)`. При N=12 p95 совпадает с максимумом; это описательная статистика малой выборки, не надёжный хвостовой SLO.
- **Память**: memory.current cgroup контейнера, замеры перед/после точки и каждые 5 секунд; sampled max — нижняя оценка возможного пика. Также сохраняется memory.peak с начала жизни Pod (не отдельной точки), memory.stat и working set = current − inactive_file. Это не RSS процесса и не RAM всего ноутбука.
- **Надёжность**: HTTP/transport/usage ошибки, изменение restartCount, дельты memory.events (OOM), cpu.stat (throttling), счётчики preemption и prefix-cache из `/metrics`, если доступны. Сам сборщик cgroup вызывает короткий python-процесс через kubectl раз в 5 секунд; этот небольшой накладной расход одинаков для серий.

Сохраняются все обезличенные запросные метрики, прогрев, cgroup-выборки, конфигурация из фактического ConfigMap, Pod UID, imageID, SHA256 входного набора и время UTC. Сырые JSON — первичный результат; таблицы и график строятся из них.

## Гипотеза настройки

`max_num_batched_tokens` ограничивает число токенов одной итерации планировщика. Снижение 1024 → 512 меняет разбиение длинного prefill и потенциальный компромисс между TTFT и пропускной способностью. Не предполагаем заранее улучшение. Установленный код vLLM `engine/arg_utils.py` проверен: chunked prefill выбирается по поддержке модели, лимит задаётся явно. Работоспособность входа 2048 при меньшем лимите проверяется реальными запросами.

Меняется **только** этот параметр. Сохраняются CPU-потоки, лимиты памяти, max_num_seqs=4, контекст 3072, KV-кэш 256 МиБ, модель и серверный imageID. B реализован отдельным Kustomize overlay `benchmarks/batch512`; исходная конфигурация проекта не редактируется. По завершении возвращаем базовый вариант независимо от того, какой быстрее.

Служебный `/metrics` фактически показывает `block_size=128`, `kv_cache_size_tokens=9344`, `enable_prefix_caching=True`; исходная строка сохранена в `05-cache-config.txt`. Уникальность первых 16 токенов входов исключает совпадение полного первого блока размером 128. Для четырёх запросов длиной 2048+64 требуется до `4 × ceil(2112/128) × 128 = 8704` KV-позиций при округлении до блока. Ёмкости хватает для этой нагрузки, но не для четырёх полностью заполненных контекстов по 3072 токена. Поэтому max_num_seqs=4 не считается обещанием четырёх максимальных контекстов без очереди.

Ограничения: одна машина, один проход A/B/A, нет контроля частот/температуры, маленькая выборка, синтетический английский текст и принудительный бюджет ответа. Разница меньше разброса A-before/A-after не считается доказанным улучшением. Даже большая разница требует повторений перед производственным решением.

Наблюдение во время A-before: macOS показывала swap `used = 6686.69M`. Между двумя диагностическими снимками вырос счётчик Swapins; это подтверждает активность подкачки в интервале, но не позволяет отнести её к конкретному процессу. В начале B значение было `used = 4190.12M`, в начале A-after — `4162.00M` (системные значения sysctl сохранены без пересчёта единиц). Снимки, временные метки и vm_stat сохранены в `05-host-observations.jsonl`; фоновые приложения не закрывались. Результаты относятся к этой системе вместе с VM и её окружением, а не к изолированной производительности CPU.

Официальные определения и параметры: [vLLM serve](https://docs.vllm.ai/en/latest/cli/serve/), [vLLM metrics](https://docs.vllm.ai/en/latest/design/metrics/). Документация latest может отличаться от закреплённого релиза; источником фактических результатов остаётся установленный 0.27.1+cpu и сохранённые ответы API.
