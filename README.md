# Запуск Qwen через vLLM на CPU

Модель работает как сервер: принимает запрос с текстом и возвращает ответ. Для запуска используются Docker и Minikube, вычисления идут только на CPU. Выбрана Qwen2.5-1.5B-Instruct и vLLM 0.27.1+cpu. 

## Как это работает

При первом запуске отдельный initContainer скачивает модель с Hugging Face в PVC. После скачивания запускается основной контейнер с vLLM. При следующих запусках модель берётся из этого хранилища.
Оба контейнера работают от пользователя 10001, без  root. Для каждого есть свой Dockerfile. Версии всех Python-зависимостей зафиксированы.

API требует Bearer-токен. Он хранится в Kubernetes Secret, отдельно от HF-токена. Параметры запуска передаются через ConfigMap. В логи контейнера пишется факт обращения, но не текст запроса или ответа. Это проверено для обычных и потоковых ответов, а также нескольких ошибок запроса и авторизации.

## Что нужно для запуска

Нужны Docker Desktop, kubectl, curl, Bash и Python 3.10 или новее. 
В Docker Desktop нужно выделить 10 Гб памяти. Кластер использует 8 виртуальных CPU и 9000 Мб памяти. У сервера лимит 6 CPU и 7,5 ГиБ памяти. 
Скрипт установки Minikube рассчитан на macOS ARM64. Проверенное окружение: macOS 26.6.2, Docker Engine 29.3.1, Minikube 1.39.0 и Kubernetes 1.34.13. 
## Первый запуск

Выполнить команды:

```bash
bash scripts/setup_minikube.sh
bash scripts/build_images.sh
bash scripts/cluster.sh start
bash scripts/cluster.sh load-images
bash scripts/deploy_k8s.sh
```
Они скачивают Minikube с проверкой SHA256, собирают два образа, создают кластер, загружают в него образы и запускают приложение. 

Веса модели занимают примерно 3,1 ГБ. Minikube, настройки доступа к кластеру и временные файлы находятся в `.cache`. Глобальный kubeconfig не меняется. Имя профиля и namespace — `kaspersky-llm`.
После запуска необходимо открыть еще один терминал в корне проекта и выполнить команду:

```bash
bash scripts/kubectl.sh -n kaspersky-llm port-forward service/vllm 18000:8000 --address 127.0.0.1
```
Эта команда делает API доступным по адресу `http://127.0.0.1:18000`. Данный терминал нужно оставить открытым. Запросы следует отправлять из другого терминала

## Как отправить запрос

Запросы отправляются через `scripts/ask.py`. Для работы клиента нужны запущенный сервер и port-forward из предыдущего шага. Команды выполняются из корня проекта в отдельном терминале.

Один вопрос:

```bash
python3 scripts/ask.py "Объясни простыми словами, что такое Docker"
```

Ответ выводится постепенно. API-токен автоматически читается из `.cache/k8s-api.env`, имя модели в API — `qwen`.

Режим диалога:

```bash
python3 scripts/ask.py
```

Вопросы вводятся после приглашения `Вы:`. История текущего разговора передаётся модели и хранится только в памяти клиента.

- `/reset` — очистка истории.
- `/exit` — выход из диалога.
- Control+C — завершение клиента.

По умолчанию длина ответа ограничена 128 токенами. Другой лимит задаётся параметром `--max-tokens`:

```bash
python3 scripts/ask.py "Объясни, как работает Kubernetes" --max-tokens 256
```

При переполнении контекста история сбрасывается командой `/reset`. При ошибке соединения или обрыве ответа выводится сообщение; неудачный обмен не добавляется в историю. Ответ отображается в терминале клиента, но не записывается в логи сервера.

## Как проверить работу

Проверки выполняются при работающем сервере и port-forward:

```bash
python3 scripts/check_smoke.py --base-url http://127.0.0.1:18000 --token-file .cache/k8s-api.env --output .cache/reports/smoke.json
python3 scripts/verify_k8s.py --output .cache/reports/kubernetes.json
python3 scripts/check_privacy.py --output .cache/reports/privacy.json
python3 -m unittest discover -s tests -v
```

Первая команда проверяет, что API возвращает HTTP 200 и непустой ответ. Затем идут 18 проверок Kubernetes, восемь HTTP-сценариев для логирования и авторизации и 18 unit-тестов.


## Где менять настройки

Параметры модели находятся в `k8s/inference.json`, настройки CPU-потоков — в `k8s/kustomization.yaml`. Сейчас используются контекст 3072 токена, до четырёх активных последовательностей, пакет 1024 токена и KV-кэш 256 МиБ. Веса хранятся в BF16, без квантизации.


Применение изменённых настроек:

```bash
bash scripts/kubectl.sh apply -k k8s
bash scripts/kubectl.sh -n kaspersky-llm rollout status deployment/vllm --timeout=900s
```

Образ пересобирать не нужно. Kubernetes заменит Pod, поэтому будет небольшой перерыв в работе. Модель останется на PVC. После замены Pod нужно заново запустить port-forward.

API-токен создаётся скриптом развёртывания в `.cache/k8s-api.env` с правами 0600 и передаётся в Secret `vllm-api`. Secret `hf-access` предназначен для HF-токена и доступен только загрузчику. Выбранная модель публичная, поэтому HF-токен для неё пустой. Передача токена для закрытой модели предусмотрена через `--hf-token-file`, но с реальной gated-моделью не проверялась.

## Нагрузочный тест

На работающем сервере с открытым port-forward:

```bash
python3 scripts/benchmark.py --results-dir .cache/benchmark-manual --label A-before
```

Скрипт использует сохранённые синтетические входы из `results/05-workload.json`: 128 и 2048 токенов, по 1, 2 и 4 одновременных клиента. Длина каждого ответа — 64 токена. Перед измерениями есть отдельный прогрев, затем по 12 запросов на каждую комбинацию. Для повторного запуска задаётся другой каталог результатов.

TTFT — время до первого текстового фрагмента ответа. Latency — время до завершения потока. Throughput — сколько выходных токенов в секунду обработала вся группа клиентов. Задержки включают очередь и передачу через port-forward.

Результаты первой серии, задержки указаны по медиане:

| Вход, токены | Клиенты | TTFT, с | Latency, с | Throughput, токенов/с |
|---:|---:|---:|---:|---:|
| 128 | 1 | 1,81 | 12,90 | 5,01 |
| 128 | 2 | 3,55 | 14,99 | 8,47 |
| 128 | 4 | 7,15 | 19,17 | 13,19 |
| 2048 | 1 | 29,52 | 42,04 | 1,16 |
| 2048 | 2 | 30,92 | 73,13 | 1,75 |
| 2048 | 4 | 51,46 | 136,89 | 1,87 |

Также сравнивался размер пакета 1024 → 512 → 1024 при четырёх клиентах. Всего успешно выполнены 120 измеряемых запросов и 30 прогревочных. Устойчивого выигрыша от пакета 512 не получилось, поэтому оставлено 1024.

Для большого потока коротких запросов стоит подбирать `max_num_seqs` — сколько последовательностей сервер может обрабатывать одновременно. В тесте рост числа клиентов с одного до четырёх увеличил throughput с 5,01 до 13,19 токена/с, но ждать первый фрагмент пришлось дольше. Лимит выше четырёх не проверялся. Размер пакета `max_num_batched_tokens` тоже нужно подбирать измерениями: меньшее значение здесь не дало устойчивого улучшения.

Для небольшого числа длинных запросов стоит проверить увеличение `max_num_batched_tokens`, чтобы обрабатывать больше входных токенов за шаг. При увеличении контекста нужно согласовать `max_model_len` и размер KV-кэша с доступной памятью. На этом Mac свободной памяти мало. В проведённом тесте переход с двух до четырёх клиентов дал всего около 6,9% прироста throughput, а время ответа почти удвоилось. Для такой нагрузки 1–2 клиента выглядят разумной отправной точкой. Увеличение пакета и кэша — возможные следующие эксперименты, их польза пока не подтверждена.

Во время измерений не было OOM и перезапусков. При этом пик памяти за время жизни Pod, включая запуск, достигал лимита 7,5 ГиБ. Выборка небольшая, на Mac работали фоновые процессы и использовалась подкачка. Эти цифры описывают конкретный запуск. p95 при 12 запросах совпадает с максимумом и не даёт надёжной оценки редких задержек.

## Как остановить и запустить снова

Перед остановкой кластера port-forward завершается через Control+C:

```bash
bash scripts/cluster.sh stop
```

Модель и секреты сохранятся. В следующий раз достаточно запустить кластер и дождаться готовности:

```bash
bash scripts/cluster.sh start
bash scripts/kubectl.sh -n kaspersky-llm rollout status deployment/vllm --timeout=900s
```

После запуска снова открывается port-forward. Удаление PVC, namespace или профиля может удалить модель.

## Что лежит в проекте

- `Dockerfile`, `requirements.txt` — образ сервера и его зависимости.
- `downloader` — отдельный образ и зависимости загрузчика.
- `app`, `config` — логирование, ревизия модели и настройки образов.
- `k8s` — основные манифесты Kustomize.
- `benchmarks/batch512` — вариант манифестов для сравнения размера пакета.
- `scripts`, `tests` — запуск, проверки и измерения.
- `results` — результаты проверок и нагрузочных измерений.
